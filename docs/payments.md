# Payments and checkout gate

The internal order/payment attempt models, provider adapters, webhook endpoints, and idempotent payment-event state processor are implemented. Stripe Checkout sessions and PayPal Orders v2 creation/capture are server initiated; provider redirects are restricted to official HTTPS hosts. Signed Stripe webhooks and PayPal's remote webhook-signature verification are normalized into internal events before state changes. Webhook request bodies are capped at 1 MiB and only a digest, event ID, amount, and currency are retained.

`commerce.payments.process_verified_payment_event` accepts normalized events only after provider verification or an authenticated PayPal capture response. It stores event IDs and payload digests, checks amount and currency against the immutable order, records provider order and transaction references, rejects mismatches, handles duplicate delivery, and prevents late failure/pending events from regressing a paid order. Raw webhook bodies are not stored. The adapter tests use provider SDK objects and mocked transport; no sandbox account or credentials were available, so these tests do not prove a live provider flow.

The adapters follow the provider-documented hosted checkout, server-side create/capture, idempotency, and webhook-signature patterns ([Stripe Checkout Session API](https://docs.stripe.com/api/checkout/sessions/create), [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests), [Stripe signature verification](https://docs.stripe.com/webhooks/signature), [PayPal Orders v2 integration](https://developer.paypal.com/api/rest/integration/orders-api), [PayPal webhook verification](https://developer.paypal.com/api/rest/webhooks/rest/)). Configure webhook URLs at `/cart/payments/webhooks/stripe/` and `/cart/payments/webhooks/paypal/` after deployment.

Customer checkout remains disabled. The order snapshot service still requires a trusted server-side shipping/tax quote, and the project has no configured market, delivery address flow, tax rules, cancellation policy, payment credentials, provider webhook IDs, or customer return/capture route. Refund operations and provider reconciliation are also not implemented. These are launch blockers; do not expose the adapters as a customer payment option until the remaining rules and workflows are built and both providers pass sandbox flows.

Never mark an order paid from a browser return URL. Never collect or store raw card data. A provider response does not establish PCI DSS compliance.

Stripe and PayPal sandbox success/failure/cancellation/refund tests and merchant configuration are launch requirements. The present suite verifies request construction, hosted URL validation, signature verification behavior, amount normalization, idempotent processing, and endpoint responses using test doubles; it does not prove sandbox connectivity or refunds.
